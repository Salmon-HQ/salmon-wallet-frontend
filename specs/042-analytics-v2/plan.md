# Implementation Plan: Analytics catalog v2

**Branch**: `feat/042-analytics-v2` (spec dir `042-analytics-v2`) | **Date**: 2026-10-19 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/042-analytics-v2/spec.md`

## Summary

The catalog grows from 9 to 20 events and gains the `powerup` prop; the batch `platform` splits `mobile` into `ios`, `android` and `seeker`. The backend allow-list ships first (a separate small change in `salmon-wallet-backend`). In the app, the shared client gets four fixes that every new event depends on: events recorded before consent is read are held instead of dropped (FR-016), the platform and the build kind may arrive asynchronously and no batch leaves before they do (FR-005, FR-014), mobile rotates its session at each open (FR-004), and delivery survives a closing window through `fetch` with `keepalive`, flushed on hide and on background (FR-015). Store builds are told apart at runtime, without new build inputs: on mobile by the EAS Update channel baked into the binary (`production`), on the extension by `management.getSelf().installType` (anything but `development`). Events are wired where the outcome is already known: `useInstalledPowerups` for installs, a new optional `onOutcome` callback on `TransactionProposal` that core calls after each signing attempt (Swap, Memo), the Payments hook, the extension's `useDAppApproval` and connect page, and the three Mobile Wallet Adapter approvals. `app_opened` reuses the wallet's own lock rule on mobile and the "not an approval launch" check on the extension.

## Technical Context

**Language/Version**: TypeScript 5.9 (React 19.2, React Native 0.86.3 / Expo SDK 57, WXT 0.21); backend JavaScript on Node 24 (Serverless v3, AWS Lambda)

**Primary Dependencies**: existing only: `expo-updates` 57.0.24 (`Updates.channel`), WXT `browser.management.getSelf`, `@solana-mobile/seed-vault-lib` through `apps/mobile/src/seed-vault/bridge.ts`. No new dependency.

**Storage**: existing analytics keys; one key constant restored, `STORAGE_KEYS.ANALYTICS_FIRST_SWAP = 'salmon_analytics_first_swap'` (the historical flag, FR-008). No new persisted data.

**Testing**: Vitest (`packages/shared`, `apps/extension`), Jest (`apps/mobile`, backend), Playwright extension suite, Maestro (Android emulator `Seeker_API35`, iOS Simulator), local backend NDJSON, staging ingest, GA4 realtime.

**Target Platform**: iOS, Android, Seeker (Android with secure Seed Vault), Chrome MV3 and Firefox extension.

**Project Type**: pnpm monorepo (mobile + extension) plus the sibling backend repo.

**Performance Goals**: an event recorded in a window that closes within 2 s arrives 10 of 10 times (SC-002); no extra request per event (one flush per hide or background).

**Constraints**: routing adds no field to events or batches; the Firefox package stays byte-for-byte reproducible (no new build input); mobile change is JS-only (no native module, fingerprint unchanged), so it can reach users as an OTA within hours, which is why the backend order (FR-019) is a hard gate; no new extension permission (`management.getSelf` needs none); a `keepalive` body stays under 64 KiB, so a flush sends at most 100 events per request (also the backend's per-batch cap).

**Scale/Scope**: 11 new events, 1 new prop key, 3 new platform values; about 25 source files across 3 packages and the backend.

## Spec vs code

1. FR-011 and the tracking plan name an approval "in the side panel when that is open". Approvals always open their own window (`apps/extension/src/entrypoints/background.ts:257-263`); the docstring above it still describes side-panel routing (`:248-251`), and the side panel forwards `CONNECT_REQUEST` to nobody (`sidepanel/main.tsx:71-74`). The plan wires the approval pages, which covers whichever window renders them.
2. Definitions name "the toolbar popup". The extension has none: `default_popup` is removed (`apps/extension/wxt.config.ts:160-172`) and the toolbar opens the side panel or sidebar (`background.ts:545-554`); `popup.html` opens only for approvals (`background.ts:191`). The Playwright suite opens `popup.html` without a hash as its main surface (`.playwright/fixtures.ts:85`), which the "not an approval launch" rule counts as an open.
3. Edge case "offline device … up to the 200-event queue bound": the client sends its whole queue in one batch (`packages/shared/src/analytics/client.ts:170`) and the backend drops everything past 100 (`salmon-wallet-backend src/analytics/handler.js:27,130`). Fixed by chunking (FR-015 row).
4. The backend still accepts `platform: 'web'` (`handler.js:26`); the web app is retired and SC-006 wants one list on both sides. Default taken: drop it (maps to `unknown`).
5. `checklists/requirements.md:36` says the consent copy waits for confirmation; the spec records it as confirmed on 2026-10-19.
6. Assumptions list store builds without `production-apk`; Definitions include it. The channel rule follows Definitions.
7. The Seeker check accepts the Seed Vault simulator in development builds (`apps/mobile/src/seed-vault/bridge.ts:114`, `__DEV__`); only non-store builds can report a simulated `seeker`.
8. `analytics/types.ts:42-44` says transports swallow their errors; the client re-queues on a throw (`client.ts:183-191`) and `transport.ts:11` throws. The comment is corrected with the transport change.
