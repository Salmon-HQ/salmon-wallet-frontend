# Research: Bitcoin network choice (spec 045)

Every claim below was checked against the code on `feat/045-bitcoin-network-choice` after merging `origin/staging` (6b98f1cb). File references are `path:line` on that tree.

## R1. Where "which networks are offered" is decided today

- **Decision**: extend the one rule, `visibleNetworkIds` (`packages/shared/src/utils/network.ts:252`), with the Bitcoin choice, through a new pure predicate `isNetworkChosen(networkId, bitcoinEnabled)` in the same file. The predicate is the single decision point; every surface that does not go through `visibleNetworkIds` calls the predicate.
- **Rationale**: `visibleNetworkIds` already feeds `useAvailableNetworks` (`hooks/useAvailableNetworks.ts:184-204`), which every chain-offering surface reads: both Homes (`apps/extension/src/pages/home/HomePage.tsx:140`, `apps/mobile/app/(app)/(tabs)/index.tsx:310`), the balance prefetch (`HomePage.tsx:274`, mobile `index.tsx:354`), Settings' network panel and address book (`hooks/useSettingsPanelData.ts:69`), and Send's contacts (`hooks/useSendContacts.ts:35`). The Bitcoin filter runs **before** the "active network stays offered" clause, so a session on Bitcoin does not keep Bitcoin on screen (that clause exists for Developer Networks, whose rule is the opposite: keep the page reachable). `network.ts` imports nothing at run time (its own note, line 102), so the predicate tests the id prefix (`networkId.split('-')[0] === 'bitcoin'`) instead of importing `getBlockchainFromNetworkId`.
- **Alternatives considered**: filtering in each Home (two copies, drifts); filtering inside `useAvailableNetworks` only (misses the four surfaces in R4–R6 that never call it).

## R2. How every reader sees the live value

- **Decision**: `useUserConfig` gains a module-level listener set. `persistPatch` (`hooks/useUserConfig.ts:117`), after the write lands, hands the merged record to every mounted instance except the one that wrote it; the writing instance already shows its own change (`commit`, line 265). Each instance registers its `applyConfig` while mounted.
- **Rationale**: several `useUserConfig` instances are alive at once (seven call sites, R2 of spec 044). Each loads the record once on mount and again only when its blockchain or environment changes (line 256), so an instance mounted before a write keeps the old value: that is why both Homes pass `developerNetworks` from the context instead of reading their own instance (`HomePage.tsx:145-149`, mobile `index.tsx:302-309`). `useAvailableNetworks` reads its own instance (`useAvailableNetworks.ts:288`), and so do `useSendContacts` (no override) and `useDerivedAccountsScan` (line 206). Without the listener the Bitcoin choice would have to be threaded as an override through four callers, and the extension's onboarding write (R7) would never reach the provider already mounted. With it, each reader stays one line.
- **Why the writer is skipped**: a second tap that lands before the first write would otherwise be overwritten on screen by the first write's merged record (which does not carry the second tap yet), the flicker the AGENTS.md settings rule forbids. Skipping the writer keeps `commit`'s optimistic state; other instances receive each merged record in order and end on the same value.
- **Ceiling, recorded**: an instance with its own optimistic change in flight that receives another instance's write shows the other record until its own write lands (two instances writing within the same few milliseconds). No screen writes from two instances at once today.
- **Alternatives considered**: an override parameter on `useAvailableNetworks` (four call-site changes, and the extension onboarding still stale); a separate React context for the choice (a second source of truth beside the settings record); reading `DeveloperModeContext` inside `useAvailableNetworks` (rejected: an import cycle, `DeveloperModeContext → useEnsureMirrorNetworks → utils/derived-accounts → hooks/useAvailableNetworks`, which `check:cycles` fails).

## R3. The stored value

- **Decision**: `UserConfig.bitcoinEnabled?: boolean` in the existing `STORAGE_KEYS.SETTINGS` record; absent reads as on. `withDefaults` does not add it, so loading an existing record writes nothing (FR-003, User Story 5).
- **Rationale**: same record and writer as Developer Networks, unverified tokens and the token list (spec FR-001: one per device). `packages/shared/src/storage` and `crypto` are not touched: Bitcoin addresses keep being derived for every phrase wallet (R5), and "Remove all wallets" does not clear the settings record (no `SETTINGS` clear anywhere in `packages/shared/src`), so a second setup's answer simply overwrites the first (FR-009).

## R4. The session standing on Bitcoin

- **Decision**: two moves, both to `solana-mainnet` through the accounts layer's `changeNetwork` (`hooks/useAccountsSelection.ts:160`):
  1. **On the switch**: `setBitcoinEnabled(false, { activeNetworkId, changeNetwork })` awaits the move before it commits, exactly as `toggleDeveloperNetworks` does (`useUserConfig.ts:305-321`). It reuses `ToggleDeveloperNetworksOptions` unchanged.
  2. **On open or after another window changed it**: an effect in `DeveloperModeProvider` (`contexts/DeveloperModeContext.tsx:45`) moves the session once the record has loaded, whenever the choice is off and `networkId` is a Bitcoin network.
- **Rationale**: the audit's "the app opens already on Bitcoin" understates it. `useHomeShell` only re-syncs the page index when the stored network is in the offered list (`hooks/useHomeShell.ts:182-183`); a stored `bitcoin-mainnet` that is no longer offered leaves `networkId` on Bitcoin for every other reader — `useBalance` would keep fetching the Bitcoin balance and Receive, Send and Activity would keep reading Bitcoin (FR-016, FR-017). The provider is mounted above every screen of the unlocked session on both apps (`apps/extension/src/AppProviders.tsx:35`, `apps/mobile/app/(app)/_layout.tsx:173`) and already reads `networkId` and the record.
- **Side effect, recorded**: `changeNetwork` reports `network_switched` with `chain: 'solana'` when analytics consent is on (`useAccountsSelection.ts:170-173`), as the Developer Networks move already does. It carries the destination family only, never the choice. Accepted by the owner on 2026-11-25 (plan.md §Owner sign-off, Q2).
- **Alternatives considered**: healing inside `useAccountsSelection` (the accounts layer does not read settings, and the spec 026 seam note in `useUserConfig.ts:41-46` explains why it should not start).

## R7. Onboarding write

- **Decision**: `saveBitcoinChoice(enabled: boolean): Promise<void>` exported from `hooks/useUserConfig.ts`, the module-private `persistPatch` behind one named entry point. The onboarding step awaits it before it moves to the password screen.
- **Rationale**: onboarding has no `useUserConfig` instance to call `commit` on. The two apps differ: mobile's provider mounts only in `(app)` (`_layout.tsx:173`), after onboarding, so it loads the record fresh on first Home; the extension's provider is mounted **above** onboarding (`AppProviders.tsx:35`; the brief's "onboarding runs before the provider mounts" holds on mobile only), its instance loaded the record at boot and does not reload when the first wallet appears (its environment stays `solana-mainnet`, `DeveloperModeContext.tsx:51-61`). Through `persistPatch` the write is serialised with every other settings write, and by R2 the extension's provider receives it at once.
- **Order of events on first Home**: the write resolved before the password step was shown → the vault is written → mobile mounts `(app)`, whose provider loads the record from storage (value present); the extension's provider already holds it. No path reads the record before the write lands.
- **Alternatives considered**: carrying the answer to the password step and writing with the vault (threads a value through `PasswordPage` and `password.tsx`, auth paths the constitution gates); calling the context setter on the extension (mobile has no provider there; two code paths).

## R8. Onboarding placement and reuse

- **Decision**: a new step between the phrase step and the password step on create and recover-from-phrase only. Extension: a new `authStep` `'networks'` in `apps/extension/src/entrypoints/popup/App.tsx` (`handleCreateComplete` / `handleRecoverComplete` go to it, it goes to `'password'`; `handlePasswordBack` returns to it). Mobile: a new route `apps/mobile/app/(auth)/networks.tsx` pushed by `create.tsx:176` and `recover.tsx:101` with the same params, pushing `/(auth)/password`. `seed-vault.tsx:86` keeps pushing the password screen directly (decision 2).
- **Screen**: made once in shared, `createNetworkChoiceScreen(kit)` in `packages/shared/src/kit/`, the spec 044 pattern (`kit/createTokenListPanel.tsx`): the platform hands it its `OnboardingLayout`, `OnboardingTitle`, `ScreenHeader`, `SettingsSelectorList` and the mark glyph. The twins are the instantiation plus navigation. The parity script pairs the mobile route with `packages/ui/src/components/AuthFlow/NetworkChoicePage.tsx` in `SCREENS` (`scripts/check-dom-parity.mjs:205-212`).
- **Options**: `SettingsSelectorList` (`types/ui/settings-panels.ts:72`), two rows with primary and secondary text, `isSelected` false for both (no preselection, FR-006), no leading well. A tap saves and continues: one screen, one tap (SC-002).
- **Step dots**: create 3 → 4 (`CREATE_FLOW_STEPS` in `packages/ui/.../CreateWalletPage.tsx:54`, `apps/mobile/app/(auth)/create.tsx:51`, `password.tsx:93`), recover 2 → 3 (`RecoverWalletPage.tsx:90`, `recover.tsx:121`, `password.tsx:95`, `PasswordPage.tsx:261`). Mobile `seed-warning.tsx:101` draws the create flow's first step with a literal `totalSteps: 3`, so it moves to 4 too. Seed Vault stays 2, which needs its own branch in mobile `password.tsx:391-392`: today every non-create flow, Seed Vault included, reads `RECOVER_FLOW_STEPS`, so raising it alone would draw Seed Vault's password screen as 3 of 3 after a first screen that said 2 (`seed-vault.tsx:98`).
- **Adding a wallet never reaches it**: both apps add wallets through the Settings account-add panel (`useAccountAddFlow`). The extension's `isAddingAccount` path into the auth flow is unreachable: `HomePage` ignores `onAddAccount` (`HomePage.tsx:118`). FR-008 holds without a guard.

## R9. Settings switch and the warning

- **Decision**: a fourth `SettingsToggleKey`, `'bitcoin'`, as the last row of Preferences in `SETTINGS_GROUPS` (`settings/registry.ts:79-148`), drawn by the toggle branch both roots already have (`SettingsPanelStack.tsx:243-270`, mobile `settings/index.tsx:253-281`). Handlers live in `useDeveloperModeToggles` (`hooks/useDeveloperModeToggles.ts`), which both roots already call: turning on writes; turning off opens the confirmation and writes only on confirm. The hook returns the confirmation's props ready to spread into `ConfirmSheet` (mobile) / `ConfirmDialog` (DOM), the existing twin pair on `ConfirmSheetPropsBase` (`types/ui/settings-panels.ts:103`), so neither root composes copy.
- **Glyph**: `CurrencyBtcIcon` from the installed Phosphor packages (`@phosphor-icons/react/dist/csr/CurrencyBtc`, `phosphor-react-native/src/icons/CurrencyBtc`), one export line in each `icons.ts`; `SettingsIconName` gains `'currencyBtc'`. No new dependency. The onboarding mark reuses `GlobeIcon`, already exported on both platforms.
- **Alternatives considered**: a new confirmation component (the brief rules it out); the switch in Advanced next to Developer Networks (owner chose Preferences).

## R10. Analytics

- **Decision**: nothing reported for the choice, on onboarding or in Settings (decision 10, FR-024). `docs/ANALYTICS.md:167` gains "Bitcoin" in the list of preferences that report nothing and a line saying the onboarding network question is not reported. The automatic move of R4 sends `network_switched` like any other switch, accepted by the owner on 2026-11-25; `docs/ANALYTICS.md` says so.
